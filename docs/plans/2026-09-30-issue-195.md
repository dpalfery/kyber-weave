**Goal:** Make live Antigravity (`agy`) OTLP telemetry attributable to the surveyed harness `antigravity` so its history is visible in sessions, rollups, and `/api/kyber/harnesses`, and repair the 11,879 misattributed stored rows in place — without weakening R6.2 (source names are never attribution evidence) and without regressing the 32 working file-side Antigravity sessions.

## 1. Problem and observed failure (issue #195, issue-reported figures)

- `records`: 11,879 rows, `source` = `agy`, `harness` = `gemini`, model `Gemini 3.8 Flash (High)`, 13 sessions, latest 2026-09-30 14:07.
- The `session` table has zero `gemini` rows; `/api/kyber/harnesses` shows gemini with 0 samples. Live agy history is invisible on every screen.
- File source `antigravity-cli` (611 checkpoints, 3,597 records) yields only 32 sessions — a secondary observation, **not** presumed a second bug (§8, task V2).

## 2. Root cause (all citations re-verified against on-disk source, 2026-09-30)

### 2.1 The span fingerprint is Antigravity's, and it carries a Gemini vendor label

The corpus fixture `dash/src/canon/adapters/__fixtures__/antigravity-span.json` (imported by `dash/src/canon/adapters/content.test.ts:3,22`) shows the live shape: attributes include `"gen_ai.agent.name": "antigravity"` **and** `"gen_ai.system": "gemini"`, Gemini-vocabulary usage counters (`gen_ai.usage.input_tokens` 251,976 including cache, `gen_ai.usage.cache_read.input_tokens` 243,910, `gen_ai.usage.cache_creation.input_tokens` 0), `copilot_chat.chat_session_id`, and `gen_ai.session.id`. `gen_ai.agent.name` is a harness-emitted attribute — admissible fingerprint evidence under the adapter contract (`dash/src/canon/adapters/base.ts:19-21`, "the only admissible fingerprint evidence").

### 2.2 No antigravity OTLP adapter exists, so the vote claims `gemini`

- `ADAPTERS` in `dash/src/canon/ingest.ts:40-45` is `[piAdapter, copilotAdapter, geminiAdapter, claudeCodeAdapter]`.
- `geminiAdapter.detect` (`dash/src/canon/adapters/gemini.ts:56-66`) awards `VENDOR_EVIDENCE` (0.6, `dash/src/canon/adapters/copilot.ts:626`) on exact `gen_ai.system === 'gemini'` plus `USAGE_EVIDENCE` (0.4, `copilot.ts:627`) on the shared input keys → 1.0 per span. `copilotAdapter.detect` explicitly yields on `gen_ai.system === 'gemini'` (`copilot.ts:644`), so Copilot does not contest it.
- Pass 1 votes per `(source, trace)` group and the winner claims the whole group at confidence ≥ `DEFAULT_CONFIDENCE_THRESHOLD` 0.6 (`dash/src/canon/adapters/registry.ts:34`, `scoreGroup`/`attribute`). Every `(agy, trace)` group therefore lands as harness `gemini` at confidence 1.0. The source name `agy` cannot save it structurally: R6.2 forbids it (`base.ts:14-16`; `ingest.ts` header; `registry.ts` header), so no rule keyed on `source` exists to divert the vote.

### 2.3 The projection intentionally drops the `gemini` identity — so the rows vanish

- `EXCLUDED_HARNESS_IDENTITIES = new Set(['gemini'])` (`dash/src/canon/measurability.ts:135`), with `GEMINI_EXCLUSION_REASON` "not a coding harness" (`dash/src/refresh/registry.ts:20-21`).
- `canonicalHarnessId` returns null for gemini (`measurability.ts:207-211`); `groupByCanonicalHarness` skips such records (`measurability.ts:213-221`); `SessionIdentities` gives excluded identities no share (`measurability.ts:254-262`).
- `buildSessions` (`dash/src/canon/sessions.ts:283-312`) sees `grouped.size === 0` → `skipped`. `buildHarnessRollup` filters `isExcludedHarnessIdentity` and "Gemini is never seeded" (`dash/src/canon/harnesses.ts:411-453`). `/api/kyber/harnesses` (`dash/src/server/routes.ts:499-506`) reads `listHarnessRollups()` — hence 0 samples. Result: 11,879 records → 0 sessions.

### 2.4 The exclusion is correct for Gemini and wrong for Antigravity

Antigravity is a **distinct surveyed harness**: `SURVEYED_HARNESSES` lists `gemini` and `antigravity` separately with the comment "folding it into `gemini` reported one harness's rollup under another harness's name" (`measurability.ts:512-532`); `normalizeHarnessName` maps `agy`/`antigravity` → `antigravity` (`measurability.ts:196`); the file side already treats it as distinct (`HARNESS_DESCRIPTORS` antigravity/antigravity-cli/antigravity-ide, `refresh/registry.ts:83-107`; `classifyAntigravity`, `registry.ts:603-617`; provider name `antigravity`, `dash/src/providers/antigravity.ts:1516`). The defect is upstream of the exclusion: **attribution files Antigravity's spans under the excluded identity**. The fix is a correct fingerprint vote, not an un-exclusion of gemini.

### 2.5 Repair machinery already exists

`renormalizeRecords` (`dash/src/tools/backfill.ts:152-244`) re-runs `ingestBatch` over stored raw payloads per trace, preserving content (`backfill.ts:217-222`), quarantining rows that still re-vote to an excluded identity as `excluded_harness` (`backfill.ts:166-199`, tail sweep `225-242`). The `renormalize` CLI (`dash/src/cli/register.ts:128-143`) runs `renormalizeRecords` then `buildSessions` — re-attribution plus re-projection in one command. `store.listHarnesses` (`dash/src/canon/store.ts:1901-1919`) observes `antigravity` from records automatically once rows carry it, and `HARNESS_DESCRIPTORS` already seeds its rollup.

## 3. Rejected alternative: source-name remap (R6.2 violation)

Remapping `source = 'agy'` → `harness = 'antigravity'` (in `toRawSpan`, a special case in the registry, or a one-off `UPDATE records SET harness`) is explicitly rejected:

1. **R6.2 is structural, not conventional** (`base.ts:14-16`): the source name participates in grouping and exact-match inheritance only; `scoreGroup` never reads it as evidence. A source-name override would be exactly the misattribution class the fingerprint vote exists to prevent — the same defect as the retired collector that took the harness from `service.name` (`ingest.ts` header).
2. **Brittle**: `agy` is today's OTLP `service.name`; a rename or per-instance suffix would silently re-hide the harness, while the attribute fingerprint (`gen_ai.agent.name`) is harness-emitted and stable.
3. **Fights the store**: attribution would disagree with the raw evidence on every future `renormalizeRecords` pass, re-quarantining or re-flipping the rows.

## 4. The change (smallest that fixes S1)

### 4.1 New OTLP adapter: `dash/src/canon/adapters/antigravity.ts`

`antigravityAdapter: HarnessAdapter`, mirroring `gemini.ts` structure (import the shared core from `copilot.ts` / `gemini.ts`; reuse `baseRecord`, `readUsageCounters`, `inclusiveConvention`, `THOUGHT_KEYS` — export `THOUGHT_KEYS` from `gemini.ts` if not already):

- `name: 'antigravity'`; `namespaces: ['gen_ai', 'gemini', 'antigravity']` (quarantine-view vocabulary, `base.ts:36-45`).
- `detect`: `gen_ai.agent.name === 'antigravity'` → `+VENDOR_EVIDENCE` (0.6); shared input keys → `+USAGE_EVIDENCE` (0.4); usage alone stays 0.4 — below the 0.6 threshold, so an agent-name-less span is never claimed on counters alone (R6.1 quarantine, not a guess).
- `relevance`: mirror `gemini.ts` (input keys 1 / output keys 0.5 / vendor key 0.1).
- `normalize`: Antigravity speaks Gemini's counter vocabulary with the same semantics the file side already records (`PROVIDER_UNMEASURABLE` antigravity family, `measurability.ts:106-110`; `HARNESS_CACHE_SURVEY` antigravity entry): cache-INCLUSIVE input, no cache-creation counter, thoughts a subset of output → `inclusiveConvention` with `cacheCreation: 0` and the thoughts key. This is the conversion those rows already receive today under the gemini label — token figures do not change, only the label.
- `unexportedMetrics(): ['cache_creation']` — agrees with the file side so OTLP and file sessions state the same limitation.

### 4.2 `geminiAdapter.detect` yields to the more-specific fingerprint

Add to `gemini.ts:56-66` (same pattern and rationale as `copilot.ts:643-645`): `if (span.attributes['gen_ai.agent.name'] === 'antigravity') return 0` — an explicit Antigravity agent identity outranks the generic `gen_ai.system` vendor label the Gemini-vocabulary exporter emits.

**Why registration order alone is insufficient (decision D2):** pass 1 averages per group. In a trace where `k` of `n` spans carry `gen_ai.agent.name`, gemini scores `n·1.0` unless it yields; antigravity scores `k·1.0 + (n−k)·0.4 ≤ n·1.0`, with equality only when `k = n` (then the tie goes to the earlier-registered adapter). So without the yield, **any** trace with even one agent-name-less span is won outright by gemini — ordering cannot fix it. With the yield, gemini averages `(n−k)/n` and antigravity `0.4 + 0.6·(k/n)`, so antigravity wins whenever `k/n > 0.375`. The yield is the load-bearing piece for mixed traces; ordering is still required for the all-spans tie and for determinism.

### 4.3 Registration (two lists, one ordering constraint)

- `ADAPTERS` (`ingest.ts:40-45`): insert `antigravityAdapter` **immediately before `geminiAdapter`** → `[pi, copilot, antigravity, gemini, claudeCode]`. Ties stay with the earlier-registered adapter (`registry.ts` `scoreGroup`, strict `>` keeps the first maximum).
- `ADAPTERS_BY_HARNESS` (`measurability.ts:369-372`): add `antigravityAdapter` so `getMeasurability` (`measurability.ts:468`) declares `cache_creation` not-measurable for OTLP antigravity sources, agreeing with the file-side declaration.
- **Constraint:** antigravity stays **after** `copilot`. `ingest.test.ts:31-41,56-67` pins an abbreviated Antigravity span (agent.name + usage + `copilot_chat.*`, **without** `gen_ai.system`) to the `copilot` label; that tie resolves to copilot only while antigravity is registered after it. Moving antigravity before copilot is decision D4, out of this fix's minimal scope.

### 4.4 In-place repair of the live store

1. Backup `canon.db` (timestamped copy; same bargain as the 2026-09-23 integrity plan Q1).
2. Pre-flight read-only measurements (§7 V1) to size the agent-name-less agy population (decision D3).
3. Run the existing `renormalize` CLI (`cli/register.ts:128-143`) with the collector quiesced: `renormalizeRecords` re-ingests each `gen_ai.system === 'gemini'` row one-span-per-batch from stored raw (`backfill.ts:166-181`); agent-name rows now re-vote antigravity (1.0 vs gemini 0) and are upserted with `harness: 'antigravity'`, content preserved (`backfill.ts:217-222`); rows that still re-vote gemini are quarantined `excluded_harness` (`backfill.ts:182-199`) — auditable, not silent. The CLI then runs `buildSessions`, which rebuilds sessions, runs `buildRuns`, rollups, and findings, and prunes stale rows.

Nothing else in the pipeline needs to change: `canonicalHarnessId('antigravity')` is `'antigravity'` (not excluded), sessions build under `SessionIdentities`, `listHarnesses` observes the harness from records, and `HARNESS_DESCRIPTORS` seeds the rollup — `/api/kyber/harnesses` shows antigravity with samples.

## 6. Risks

1. **geminiAdapter behavior change (the yield):** fires only on spans carrying `gen_ai.agent.name === 'antigravity'` — Antigravity's agent identity, which genuine Gemini CLI telemetry does not assert. Pinned by T2. Genuine gemini-labeled data remains quarantined as `excluded_harness`, unchanged.
2. **Threshold/tie effects on other harnesses:** pi and claudeCode are untouched; copilot's position is unchanged and the yield removes the only overlap. The one deliberate tie preserved is copilot-over-antigravity for the abbreviated corpus shape pinned at `ingest.test.ts:56-67` — a documented constraint (D4), not an accident.
3. **Live-DB migration:** rows that re-vote gemini (agent-name-less agy spans) move from invisible `records` rows to auditable `excluded_harness` quarantine — a state change requiring the pre-flight count (V1) and decision D3. The backup bounds the blast radius; `renormalizeRecords` is idempotent over raw evidence.
4. **The 32 file-side sessions:** the file path (`codeburn/antigravity*` sources) is untouched by the adapter change, and `renormalizeRecords` only quarantines excluded-harness rows — file-sourced rows carry `antigravity*` harness ids. V3 gates the repair on the 32 sessions (and the 611 checkpoints / 3,597 records) being unchanged; any delta is a stop-and-investigate, not a presumption.
5. **Identity seams:** OTLP sessions key on `COALESCE(session_id, trace_id)` (`store.ts:1487-1522`); agy spans carry both `gen_ai.session.id` and `copilot_chat.chat_session_id` (`canonicalSessionId` reads them in that order, `copilot.ts:SESSION_ID_KEYS`), so OTLP sessions stay distinct from file-side ones under the surveyed split ids — `split-identity.test.ts` owns this; T5 extends it.
6. **Token/cost regression:** none intended — the conversion is byte-identical to what these rows already receive under the gemini label; `ingest.test.ts:69-83` (the 1.97× double-count regression) keeps pinning the inclusive convention.
