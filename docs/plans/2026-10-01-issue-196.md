# Fix KyberDash Codex session ingestion and display — #196

Fixes [issue #196](https://github.com/dpalfery/kyber-weave/issues/196): "KyberDash: Codex ingests 647 folder sessions but shows 5; no codex-cli or collector data".

**Development mode: test-first.** Every task names its failing test first.

## Summary

The Codex provider discovers 647 sessions on disk but KyberDash dashboard shows only 5 sessions. This plan addresses three related breakages revealed after PR #230 (issues #189, #198, #199) merged coverage-window and collector-activity improvements:

1. **Session discovery vs. ingest mismatch:** The Codex file parser discovers far more sessions than appear in the canonical store; the gap is unexplained and not attributed to the coverage window.
2. **Codex-cli missing from surfaces:** Codex sessions attributed to the `codex-cli` originator are discovered but missing from the dashboard.
3. **No collector (OTLP) data for Codex:** Live OTLP telemetry for Codex workflows is not being surfaced or is missing entirely; both file-source and live-telemetry paths should work.

The discovery-vs-store gap, codex-cli attribution, and collector data availability must be jointly diagnosed and fixed with a single test contract to avoid partial repairs that hide downstream issues.

## Open questions (decision ledger)

### D1 — Single or dual provider for Codex?

**Question:** Should `codex-cli` be a separate provider from `codex` (Desktop), or should one provider handle both with an originator filter?

**Options:**
- *A:* One `codex` provider; internal logic distinguishes CLI vs Desktop via `originator` field.
- *B:* Separate `codex-cli` provider alongside `codex`; registry lists both.

**Recommendation:** *A* (one provider, internal originator branching). Codex CLI and Desktop write to the same `~/.codex/sessions` tree with different originators; splitting into two providers duplicates discovery and creates sync risk. The registry can distinguish them at display level (`harnessFamily`, harness rollup label) without a second provider.

**Decision (Approved 2026-10-01):** *A* — One `codex` provider with internal originator branching. No separate `codex-cli` provider; originator field drives display-level grouping in harness matrix and session list.

### D2 — Collector data expectation for Codex

**Question:** Should this plan expect Codex CLI to emit OTLP spans to port 4318, or is that a separate owner-configuration task?

**Options:**
- *A:* Assume Codex CLI does not emit OTLP; focus on file-source sessions only.
- *B:* Assume Codex CLI can emit OTLP; verify the collector path works (receiver accepts, ingest correlates, spans surface).
- *C:* Defer collector data as a post-merge owner task.

**Recommendation:** *B* (verify both paths). If the collector receives Codex spans but they're being quarantined, that's a fixable issue. If no spans arrive, that's an owner task. Plan should not assume or leave ambiguous which case holds.

**Decision (Approved 2026-10-01):** *B* — Verify both file-source and collector paths. T4 tests confirm whether OTLP spans are accepted, quarantined, or absent; deferred owner tasks are identified by diagnostic outcome.

### D3 — Build Codex OTLP adapter now, with source-verified names and owner-capture gates?

**Question:** Primary-source research (OpenAI Codex main) verified that Codex exports OTLP logs+spans with documented attribute names (service.name: codex_cli_rs/codex_exec/codex-app-server, model+slug, conversation.id, tokens). Three items remain UNVERIFIED (span name, trace_id/span_id in logs, token convention). Should this plan build T4 now with source-verified names and mark unverified items as explicit owner-capture blockers, or wait for the owner to capture a real payload first?

**Options:**
- *A:* Build T4 now using source-verified names and fixture derived from verified attributes. Mark three unverified items as owner-capture checks (explicit blockers for production span accuracy).
- *B:* Wait for owner to capture a real payload first; then build T4 with all facts verified (lower fabrication risk, but defers delivery).
- *C:* Skip adapter; this plan fixes file-source (T3) and makes collector quarantine reason auditable.

**Context:** Scope now includes Codex OTLP adapter (lifted "no new adapters" restriction). Source verification provides high confidence on service names, attributes, token fields. Three unverified items are flagged as explicit owner tasks; adapter fingerprint must not depend on service.name (rule R6.2). Log enrichment for model (present on log events but not span handle_responses) requires decision in T4b.

**Recommendation:** *A* (build T4 now with source-verified names and owner-capture gates). Test fixture is derived from verified attribute schema, not guessed. Owner captures fill the three gaps before production use. This closes the collector-path gap in one delivery; T3+T4 together make Codex discovery-vs-ingest honest.

**Decision (Approved 2026-10-02):** *A*.

**Blocking:** T4 scope and tasks (T4a, T4b).

**Key facts:**
- (a) In-window Codex rollouts → `record_count > 0` ✓
- (b) Pre-window rollout silently dropped by `sliceCallsToWindow`, checkpoint persisted with status=ok / record_count=0 / no reason
- (c) In-window session with no token_count/model events → 0 calls parsed, identical silent checkpoint
- (d) **Classification already splits codex-cli/codex-desktop/codex-unclassified** (classifySessionSource, registry.ts ~562-655), no dedup collisions — **D1 hypothesis refuted, originator is preserved**
