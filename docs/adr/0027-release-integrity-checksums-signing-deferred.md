# ADR 0027: Release Integrity via SHA-256 Checksums with Code Signing Deferred

## Status

Accepted, 2026-09-29. Records the decision to rely on SHA-256 checksums for release integrity, with Authenticode and GPG signing deferred and Azure signing ruled out on cost.

## Context

The Windows tray installer (`kyberdash-tray-win-x64-setup.exe`) and Windows CLI, MCP, and KyberDash `.exe` binaries are not Authenticode-signed. Users downloading binaries from the GitHub Releases page encounter a SmartScreen warning on Windows, and have no documented way to verify that a download is intact. The macOS tray is Developer ID-signed and notarized; Linux binaries are unsigned, as is normal for Linux.

The release workflow produces 20 binary artifacts plus a manifest file, across five groups: CLI (5), MCP (5), KyberDash (5), tray (3), and Squad (2). Previously, the published `SHA256SUMS.txt` listed a per-RID manifest file that was generated by each build job; the release job would merge these, then run `sha256sum *` which included the stale per-RID copy, and the result was a manifest that listed itself with a hash that could not match the final published file. As a result, `sha256sum -c SHA256SUMS.txt` would report a failure for that line. No step validated that the manifest was complete and correct or that the asset set matched the expected release.

Every shipped binary already ships over HTTPS. The choice is what integrity mechanism to use when HTTPS alone is insufficient — either cryptographic signatures (Authenticode, GPG, or a signing service), hash verification through a manifest, or both.

## Decision

1. **Release integrity rests on HTTPS plus a complete `SHA256SUMS.txt` that covers every release asset.** The manifest is generated once per release from a declared expected asset list. No asset is added to the list without an explicit change. A pre-publish check runs before `gh release create` and fails the job (fail-closed), preventing publication if any expected asset is missing or any unexpected asset is present. A post-publish check runs after `gh release create` and fails the job if the published assets do not match the expected set or if the published manifest does not byte-match the local copy, but the release is already public (detective only, not preventive).

2. **Windows binaries are not Authenticode-signed for now.** Both the tray installer and the `.exe` files inside CLI, MCP, and KyberDash archives remain unsigned. SmartScreen warns on first run; the flow is documented.

3. **No GPG-signed manifests are published.** The manifest itself is not signed; integrity rests entirely on HTTPS transit protection and the hash check that downstream users perform.

4. **Azure signing (Trusted Signing / Key Vault) is ruled out on cost.** An EV certificate was not evaluated and is not pursued.

5. **SignPath Foundation is a possible free option for open-source projects; eligibility and terms have not been verified.** GitHub issue [#132](https://github.com/dpalfery/kyber-weave/issues/132) is the tracker and is labelled `deferred`.

6. **macOS tray Developer ID signing is unaffected.** The tray for macOS is Developer ID-signed by team `J2UNNQ466J` and notarized; this remains the case.

## Alternatives considered

- **Authenticode signing of Windows binaries with an EV certificate or Azure signing (Trusted Signing / Key Vault).** Azure signing (Trusted Signing / Key Vault) was ruled out on cost. An EV certificate was not evaluated and is not pursued. Signing of any kind would need a signing service integrated into the release workflow.

- **GPG-signed manifests.** Would allow downstream users to verify that the manifest itself came from the project. GPG-signed manifests are not pursued; the manifest is unsigned and integrity rests on HTTPS transit plus the hash check (Decision 3).

- **Deferred Authenticode only (no manifest completeness check).** Would defer the signing infrastructure cost but leave the defect in place where the manifest lists itself with a stale hash. Fails the goal of making the release fail when assets are missing or unexpected.

## Consequences

- **SmartScreen warnings persist on Windows until signing is adopted or reputation builds.** Users typically see a SmartScreen warning on first run with text similar to "Windows protected your PC", with documented steps to click **More info** and then **Run anyway**; the exact wording varies by Windows build. Mark-of-the-Web quarantine applies to `.exe` files extracted from a downloaded zip archive, requiring users to unblock the file (via Properties → **Unblock** or the `Unblock-File` PowerShell cmdlet). This flow is documented in `docs/install.md#windows-unsigned-binaries-and-smartscreen`.

- **Manual hash verification is the integrity control.** Users on Windows verify with PowerShell (`Get-FileHash`); macOS and Linux users use `shasum` or `sha256sum`. The verification procedure is documented in `docs/install.md#verifying-a-download`.

- **Adding a new release asset requires editing the expected asset list in `scripts/verify-release-checksums.sh`.** The `EXPECTED_ASSETS` array is the single source of truth for completeness validation. Both the pre-publish check and the post-publish `--list` call read this array. A missing edit causes the release to fail at the manifest step, before `gh release create` runs; the matching build job and the count test must also be updated. This is documented in `docs/distribution.md#code-signing-status` as maintainer guidance.
