# ADR 0002: Three-Layer Code Review Council with Deterministic Verdict Engine

## Status

Accepted; amended 2026-11-02 to record the retirement of `NEEDS_HUMAN`, `always-human` (`KW-REVIEW-008` / `KW-REVIEW-011`), and `max-reviewable-lines` (`KW-REVIEW-009`) in favor of a binary `APPROVE` / `REQUEST_CHANGES` verdict.

## Context

The legacy `code-reviewer` architecture was a single agent executing a single serial prompt across multiple review concerns. This design suffered from three structural defects:
1. **Unexecutable Execution Mandates**: The reviewer's capability profile denied command execution (`process.execute: deny`), yet instructions demanded running builds, inspecting test logs, and checking coverage. This forced the agent to either skip verification or fabricate unverified claims.
2. **Context Dilution and Attention Saturation**: A dozen disparate concerns (dependency supply chain, security STRIDE, DI patterns, error handling, static analysis triage) were evaluated in one context window, applying equal attention to trivial and high-risk diffs.
3. **Subjective, Non-Auditable Verdicts**: The final approval verdict was generated by the same LLM that generated findings ("verdict as a vibe"), making review outcomes non-deterministic, untestable, and impossible to audit.

## Decision

We replace the single-prompt reviewer with a three-layer review architecture separating measurement, evaluation, and adjudication:

1. **Deterministic Gate Layer (`kyber-weave review gates`)**:
   - Executes host-declared commands (`review.gates` in `.kyber-weave/kyber-weave.yml`).
   - Gate commands are parsed and executed strictly as `argv` arrays via `ProcessRunner` without shell expansion or concatenation, eliminating command injection risks.
   - Gate outputs produce machine-readable evidence files under `artifacts/`.

2. **Parallel Agentic Council Layer**:
   - Decomposes review into specialist lenses (e.g. `intent-alignment`, `dependency-supply-chain`, `test-adequacy`, `prior-art`, `duplicate-implementation`, `static-analysis-triage`).
   - Lenses fan out in parallel and evaluate diffs independently against declared applicability predicates, auto-skipping when unaffected.
   - Separated into `review-lens` (`model-profile: general`) for architectural judgement and `review-triage` (`model-profile: fast`) for mechanical triage.
   - Mandatory finding schema requiring `excerpt`, `evidence`, and falsifiable `failure_scenario`.

3. **Deterministic Verdict Engine (`kyber-weave review verdict`)**:
   - Implemented as unit-tested C# code (`KyberWeave.Core/Review`, `KW-REVIEW-*` rule family), completely independent of model inference.
   - Evaluates findings and gate outcomes against repository policy (`review.policy`, confidence/severity thresholds).
   - Generates structured SARIF reports and deterministic binary verdicts: `APPROVE` (0) or `REQUEST_CHANGES` (1).
   - *Amendment (2026-11-02)*: The owner directive retired `NEEDS_HUMAN`, `always-human` path globs (`KW-REVIEW-008`, `KW-REVIEW-011`), and `max-reviewable-lines` (`KW-REVIEW-009`). Verdicts are strictly binary: clean runs approve (0); any blocking gate failure, critical finding, or exceeding major findings requests changes (1).

## Alternatives Considered

- **Single serial orchestrator evaluating all concerns**: Rejected because monolithic context windows degrade inspection quality and increase inference cost.
- **LLM-generated approval verdict**: Rejected because model-generated verdicts cannot be unit-tested or audited, and yield non-deterministic results on identical diffs.
- **Shell-based gate command strings**: Rejected because shell pipelines and string concatenation expose repositories to prompt injection and command execution vulnerabilities from untrusted diffs.

## Consequences

- Review verdicts are completely auditable, deterministic, and backed by unit tests (`VerdictEngine`).
- Gate commands execute safely without shell vulnerabilities.
- Review lenses focus exclusively on their domain of expertise and auto-skip irrelevant changes.
- *Amendment (2026-11-02)*: Verdicts are binary (`APPROVE` or `REQUEST_CHANGES`). Sensitive paths and diff sizes no longer escalate to `NEEDS_HUMAN`; gates and findings alone determine acceptance.
