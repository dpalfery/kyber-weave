One PR fixing three GitHub issues in [dpalfery/kyber-weave](https://github.com/dpalfery/kyber-weave) on branch `fix/dash-181-182-191-findings-quality` (off `origin/main`, HEAD includes merged #184 at `61265428`):

- [#182](https://github.com/dpalfery/kyber-weave/issues/182) — one session counted under two harnesses (`claude-desktop:X` vs `claude-code:X`, `cursor:X` vs `cursor-agent:X`); the identical 790,615-token peak appears twice in the top-5; the compare run picker lists both twins; runs/findings/waste are inflated.
- [#191](https://github.com/dpalfery/kyber-weave/issues/191) — Context Doctor shows only 5 of 115 findings (requests `/findings?limit=10`, renders `maxItems={5}`); no show-all, no detector/harness filter, no per-detector counts; 49 duplicate-tool-call findings are invisible from the workspace view.

## Background and goal

KyberDash derives sessions, runs, executions, and findings from canonical records (`dash/src/canon/`), serves them over `dash/src/server/routes.ts` + `bridge.ts`, and renders `dash/web/src/`. Findings are a rebuildable cache: `buildFindings` (`dash/src/canon/findings.ts:33-87`) runs the pure detectors (`dash/src/analysis/findings.ts`) per run and prunes anything not re-emitted (`canon/findings.ts:79-84`), so detector and identity fixes take effect on rebuild with no migration.

Goal: after this PR, every persisted finding is (1) attributed to the agent harness that actually produced it, not the front-end that exported the telemetry; (2) measured only against denominators and numerators telemetry actually supports, with unknown windows surfaced as unknown; and (3) fully inspectable from the Context Doctor workspace view, so detector quality is auditable.

## Shared root cause analysis — one theme, three failure layers

There is one theme: **the findings pipeline presents as deterministic measurements things that were never measured** — and the workspace view's 5-finding window (191) is what let the fabrication (181) and double-counting (182) go unaudited.

1. **Identity integrity (#182):** canonical identity follows the *export front-end* instead of the *harness*. `normalizeHarnessName` deliberately keeps `claude-desktop` ≠ `claude-code` and `cursor` ≠ `cursor-agent` distinct (`dash/src/canon/measurability.ts:176-186`), so `SessionIdentities` (`measurability.ts:249-293`) splits one session key into `${harness}:${key}` shares, `buildRuns` (`dash/src/canon/runs.ts:398-494`) mints one execution/run per share, and `buildFindings` re-emits the identical finding twice. The store's own comment admits the truth — "one harness reached through two front ends … is one harness" (`dash/src/canon/store.ts:1487-1504`) — but the identity layer never encoded it.
2. **Honest measurement (#181):** the detector borrows the named 200,000 fallback (`dash/src/canon/context-window.ts:22, :71`) as a *denominator* and fires at 85% of it (`dash/src/analysis/findings.ts:1036-1050`), stamping the result `confidence: 'deterministic'` / `measurementClass: 'deterministic'` (`:1095, :1106`) even though its mechanism text confesses the guess (`:1082-1087`). Symmetrically, the *numerator* is trusted: a per-record token figure (`:1009`) that plausibly aggregates child calls is presented as one turn's consumption. Both violate the honest-unobservability rule (unknown window must surface as unknown, never silently defaulted) — and the UI caption "~75%" (`dash/web/src/components/analysis/ContextPressureStrip.tsx:116`) disagrees with the detector's 85% (`findings.ts:1049`).
3. **Full visibility (#191):** the API serves at most a `limit` slice with no total, offset, detector, or server-side harness filter (`dash/src/server/routes.ts:391-407`, `bridge.ts:1862-1868`, `store.ts:2039`), the client filters harness after fetch (`dash/web/src/lib/kyberApi.ts:664-666`), and Context Doctor fetches 10 and renders 5 (`dash/web/src/pages/ContextDoctor.tsx:106-110, :148-156`). The plans inventory already carries this as a known residual: "findings client-side harness filter … not claimed shipped" (`docs/plans/README.md`).

Fix order follows the dependency: identity first (it changes the corpus every detector reads), then the detector, then the API/UI that surfaces the result.

## Root cause and smallest change, per issue

### #182 — twin harnesses (identity layer)

**Root cause (evidence):** `normalizeHarnessName` returns `claude-desktop` and `cursor-agent` as their own canonical ids (`measurability.ts:176-186`: `claude-cli`/`claude-desktop`/`claude-unclassified` pass through at `:178`; `cursor-agent` at `:185`, `cursor` at `:186`). `canonicalHarnessId` (`:207`) and `groupByCanonicalHarness` (`:212`) feed those distinct ids into `SessionIdentities` (`:249`), which assigns a bare key only when a key has exactly one canonical harness (`:265`) and otherwise mints `${harness}:${key}` (`:285-293`). `buildRuns` then produces one candidate per (sessionKey × canonical-harness share) (`runs.ts:406-437` via `groupByCanonicalHarness` + `identities.claim`), so twin shares become two executions → two runs → two identical findings (`findings.ts:977-1005` mirrors the same split in the detector). `sessionKeys()` already groups by raw `COALESCE(session_id, trace_id)` and only normalizes the label afterwards (`store.ts:1504-1521`), and `listHarnesses` dedupes only normalized *names* (`store.ts:1901-1919`) — so both twins survive to every derived surface.

**Smallest change:** collapse the two evidenced front-end pairs at the one home every consumer already reads — `normalizeHarnessName`:

- `claude-desktop` → `claude-code` (the desktop app's OTLP export is Claude Code; the store comment at `store.ts:1487-1490` already asserts this equivalence).
- `cursor-agent` → `cursor` (Cursor Agent is Cursor).

Raw records keep their front-end harness string as provenance; every *derived* surface (session/run/execution rows, `canonicalHarnessId`, `SessionIdentities`, `listHarnesses`, run picker, findings `payload.harness` stamped in `canon/findings.ts:70`) collapses to one owner id with no further code changes. Runs/executions/findings are rebuildable derived tables (ADR 0008/D13, `runs.ts:1-4`); a rebuild dissolves existing twin rows. `claude-cli`, `claude-unclassified`, and the copilot surface ids stay distinct — no corpus evidence they twin, and folding an *unclassified* id into a specific surface would claim knowledge telemetry does not carry (see Q2).

**Blast radius (test updates are the deliverable, not collateral):** `dash/src/canon/split-identity.test.ts:63` (`cursor-agent`→`cursor-agent`), `dash/src/canon/measurability.test.ts:435`, `dash/tools/parity-survey.test.ts:137` pin the old outputs and flip to the new contract; check `SURVEYED_HARNESSES`/`SURVEY_FAMILY` (`measurability.ts:160-172`) for a `cursor-agent` row and fold it. External bookmarks like `/runs?harness=cursor-agent` stop matching — accepted, the id was wrong.

### #181 — guessed window, aggregate peak, 85 vs ~75 (detector + gauge)

**Root cause (evidence):**

- *Guessed denominator:* `contextLimitOf` falls back to `DEFAULT_CONTEXT_LIMIT = 200_000` with `contextLimitSource: 'default'` when no record reports a window (`context-window.ts:22, :36, :71`). `detectCompactionHazard` uses that window (`findings.ts:1036-1040`), fires when `peak > floor(limit * 0.85)` (`:1049-1050`), and stamps the finding deterministic (`:1095, :1106`) — even though `windowPhrase` at `:1082-1087` itself names "the 200,000 default; no source reported a window". A ratio against an invented denominator is not a measurement.
- *Trusted aggregate numerator:* peak tokens per turn record are `reportedInput || fresh + cacheRead + cacheCreation` (`:1009`); a Copilot record whose `reportedInput` aggregates child calls (1,278,417 = 639% of 200K) is presented as one turn's consumption, which is physically impossible against any window that served the call.
- *Threshold disagreement:* detector and finding text say 85% (`:1049`, mechanism `:1083-1086`); the gauge caption says "Compaction threshold (~75%)" (`ContextPressureStrip.tsx:116`) with no 75% logic anywhere else — stale copy, not a second threshold.

**Smallest change (three guards in `detectCompactionHazard`, one caption):**

1. **Default window ⇒ no finding.** After window derivation (`findings.ts:1036-1040`): when `contextLimitSource === 'default'` and no caller-declared `input.contextLimit`, skip the group — no ratio, no `estimatedWasteTokens`, no finding. The honest state ("context window unreported — pressure unmeasurable") is surfaced where pressure is shown: the strip already has an `isUnmeasurable` branch with a reason (`ContextPressureStrip.tsx:22-44`). Rule id `compaction-hazard` is unchanged (rule ids are permanent). The existing canon test that pins default-window *firing* with provenance (`dash/src/canon/findings.test.ts:13-28` contract comment) is rewritten to pin the new no-finding contract.
2. **Reported window, peak > window ⇒ downgraded finding, not a percentage claim.** If `peakTurn.tokens > limit` with a *reported* window, keep the signal but stop claiming a deterministic single-turn measurement: `confidence: 'heuristic'`, `measurementClass: 'inferred'` (both existing ontology values — no widening), mechanism states the peak exceeds the reported window so token attribution likely aggregates child calls, payload keeps `contextLimit`/`contextLimitSource: 'reported'`. `estimatedWasteTokens` stays `peak − threshold` (both measured against a real window); error bar stays.
3. **Caption reconciliation.** `ContextPressureStrip.tsx:116` caption becomes "Compaction threshold (~85%)" to match the detector (`findings.ts:1049`) and finding text. Drawing an 85% tick on the track is a non-goal.
4. **Version stamp.** Bump `DETECTOR_VERSION` (written to store metadata at `dash/src/canon/store.ts:393-397`) so rebuilt findings are traceable to the changed detector semantics.

`context-window.ts` itself is untouched: the named default and provenance type remain the shared derivation (`context-window.ts:1-13` header contract); the change is that the *compaction detector* refuses to divide by it.

### #191 — only 5 of 115 findings visible (API + UI)

**Root cause (evidence):** the route accepts only `runId`/`sessionId`/`limit` (`routes.ts:391-407`); `bridge.listFindings` slices by limit with no offset/total/filter (`bridge.ts:1862-1868`); `store.listFindings(runId, sessionId)` filters nothing else and is documented as such (`store.ts:2038-2045`); `docs/dash/architecture.md:557` documents the contract as `?runId=`, `?sessionId=` only. The client then filters harness *after* fetch (`kyberApi.ts:664-666`) — the residual the plans inventory never claimed shipped — and Context Doctor fetches `{limit: 10}` (`ContextDoctor.tsx:106-110`) into `FindingList maxItems={5}` (`:148-156`; `FindingList.tsx` props at `:6`). 105 of 115 findings never reach the client; per-detector counts (e.g., 49 duplicate-tool-call) are unknowable from the workspace view.

**Smallest change:**

- **Server (additive envelope, no schema change):** `GET /api/kyber/findings` gains `?detector=`, `?harness=`, `?offset=` alongside `limit`; response becomes `{ findings, total, limit, offset, detectorCounts }` where `total`/`detectorCounts` reflect the filtered set *ignoring* limit/offset. Existing callers read `json.findings` and keep working. Implementation: extend the route (`routes.ts:391-407`), `bridge.listFindings` (`bridge.ts:1862`), and `store.listFindings` (`store.ts:2039`) to an options object — `detector_id` is a real column (`store.ts:247-249`) so it filters in SQL; `harness` rides in the finding payload (`canon/findings.ts:70`, round-tripped by `toFinding`, `store.ts:826+`; asserted top-level in `dash/src/canon/sessions.test.ts:479-485`) and filters in the bridge before limit/offset slicing — no migration.
- **Client:** `fetchFindings` (`kyberApi.ts:651`) passes `harness`/`detector`/`offset` server-side (drop the client-side filter, `:664-666`) and returns the envelope; `HarnessDetail.tsx:67` switches to the server-side `?harness=` (closes the plans-inventory residual).
- **Context Doctor UI:** keep the top-5 "Highest-Leverage Workspace Findings" card; add an "All Workspace Findings (N)" section below it — per-detector count chips (toggle filter), harness select built from the already-observed harness list (`ContextDoctor.tsx:71, :113-124`), and paginated rendering (page size 25, "Load more") reusing `FindingCard`/`FindingList` without `maxItems`. `FindingList` needs no new pagination props; the page owns offset state.

## Live evidence (Stage 2 Condition 1)

Read-only bounded queries against the live store (`sqlite3 -readonly ~/.kyberdash/canon.db`, `.timeout 5000`, `LIMIT`s; no writes) on 2026-09-30, plus the local dashboard at `:4747`. Corpus: `claude-code` 8,214 records, `claude-desktop` 17,491, `cursor` 20,860, `cursor-agent` 17.

- **Claude twins OVERLAP (same turns, two collectors).** Key `4dd19692-…-b1d3eec`: 6 `llm.invoke` rows under `claude-code` (source `claude-code-desktop`, bare-hex span ids = OTLP) + 6 under `claude-desktop` (source `codeburn/claude-desktop`, `synth:` span ids = transcript files). Span ids are disjoint; timestamps interleave within ~2–6 s; **token payloads are byte-identical per turn** (e.g. `reportedInput` 64075, 65863, 66314 each appear under both harnesses — 1 OTLP row + 2 file rows per turn). A bare harness fold would sum the same turn 2–3× and inflate session totals. Larger twin keys exist (`3c861778-…` 3,623 rows; `511680a9-…` 2,560).
- **Cursor twins are DISJOINT (complementary coverage).** Key `0f659701-…-94ae9`: 3 `cursor` file rows (request/response halves: `17007/0`, `0/45`) + 1 `cursor-agent` row (`125/45`) at distinct timestamps with distinct counters. A fold sums the union of disjoint spans — no inflation from the fold itself (residual `45`-output overlap noted as follow-up, amounts trivial).
- **Consequence:** per ADR 0009 D4 ("counters come from the OTel row; content comes from the file row … Values are never summed across sources for the same turn"), this PR implements fold PLUS cross-source same-turn dedupe (`dedupeTwinTurns`, new `dash/src/canon/twin-dedupe.ts`): within one merged canonical-harness group, `llm.invoke` rows from differing sources (one file, one OTel) with identical six-counter payloads and timestamps within 60 s (named `TWIN_TURN_MAX_SKEW_MS`; live skew observed <10 s) collapse to one turn — OTel counters kept, file content transplanted when the OTel row carries no parts. Applied at the three derived-layer merge points (`buildSessions`, `buildRuns`, `buildFindings` record gathering). Test proves merged session totals equal the OTel-only totals.
