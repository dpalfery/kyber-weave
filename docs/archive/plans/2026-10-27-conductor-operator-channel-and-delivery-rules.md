**Scale:** `extends-component`, component `KyberSquad`.

**Scope:** two objectives in one plan.

- **Objective A.** In an autonomous run inside an Azure Container Apps (ACA) sandbox on **Copilot CLI, global scope only** (`$COPILOT_HOME/agents`), the conductor may call exactly one messaging MCP server, under the generic alias `operator-channel`, when `KYBER_SQUAD_OPERATOR_CHANNEL` is exactly `true` at render. It sends a hard-block question and waits, bounded, for the operator's reply. Default output for every harness and every other install stays byte-identical.
- **Objective B.** New delivery rules for the conductor and the review surfaces, in both modes:
  - Commit, push a feature branch, and open a **draft** PR without waiting for the council.
  - Mark the PR ready for review as soon as every required CI check passes on the head commit. No review and no human approval is needed first; bot or human review happens after the PR is ready.
  - Never merge, and never push to the default branch. The merge/publish/delete/spend hard stop stays.
  - In **autonomous** mode, a `NEEDS_HUMAN` verdict (including `KW-REVIEW-008` on agent instruction files and `KW-REVIEW-009` size) is a finding to report, not a stop. The run delivers, lists the verdict in the PR description, and the PR still goes from draft to ready on required CI. The draft PR is the human review (U1).

## 1. Problem and goal

### 1.1 Problem

- **A.** The conductor's tools are fixed at render time by the capability profile `orchestrator`. The Copilot renderer emits the conductor's exact `copilot-tools` list (`conductor.md` line 8), with no MCP server. `conductor.md` line 22 forbids MCP use. In an unattended sandbox nobody sees a hard block until someone looks, and the run cannot get an answer.
- **B.** The conductor says "Do not commit, push, publish, or open a pull request until the council returns `APPROVE`" (`execution-and-review.md` line 76), "leave it unpushed" (`autonomy.md` line 44) and "Do not mark the pull request ready for review" (`autonomy.md` line 56). `code-reviewer.md` and the code-review pre-push gate say the same. The owner now uses CI as the only gate for **ready**, with review after ready, and wants pushing a draft to be routine in both modes.

### 1.2 Goal

- **A.** With the gate off (the default everywhere), the rendered output for all thirteen targets, both scopes, is byte-identical to today, including degradation records and warnings. With the gate on, for the **Copilot CLI global-scope render only** (Q8; project installs, VS Code and the cloud agent get the not-rendered record), and only when `operator-channel` is declared in the Copilot CLI MCP config visible at render, the conductor gains exactly one tool entry `operator-channel/*` and one instruction section. Everywhere else nothing is rendered and a degradation record or warning says why.
- **B.** No conductor or review text forbids committing, pushing or opening a draft PR. A single "ready for review" rule replaces "do not mark ready": ready once every required CI check passes on the head commit. Kept: "Never merge", "never the default branch", the merge/publish/delete/spend hard stop.

## 8. Risks

- **Render-time vs runtime env.** If the sandbox sets the var only at agent start, the overlay is absent. Mitigation: H3; doctor reports the mismatch.
- **MCP config via flag.** `--additional-mcp-config` is invisible to the probe; the feature renders nothing (safe, but inert).
- **Wait bound is partly instruction-level.** The model counts receive calls; the server-side 30-minute expiry is the deterministic backstop (G2).
- **Reply authenticity** rests on the server (G6).
- **Supervised behaviour change** (D10): drafts are pushed, and marked ready on green CI, without asking.
- **Autonomous delivery of reserved-path changes** (U1): a change to capability profiles or agent instructions can reach a ready PR with no human in the loop. Merge stays human, and `KW-REVIEW-008` stays visible in the PR description (Q9).
- **Ready without any review** (Q7) is the owner's choice. Council findings, parked items and open findings are flagged in the PR description, and review happens after ready.
