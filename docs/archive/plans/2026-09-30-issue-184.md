# KyberDash: turn inspector empty content and mixed turn numbering (issue #184)

Archived 2026-09-30 at PR [#217](https://github.com/dpalfery/kyber-weave/pull/217) close; implementation complete, decisions Q1–Q3 approved 2026-09-30 as recommended. No ADR — the convention fix follows the existing payload contract and ADR 0014's unclipped-turn-inspection protocol.

Fixes [issue #184](https://github.com/dpalfery/kyber-weave/issues/184) (S1): `/session/<id>/turn/5`
shows every block "empty"/"n/a", "No content recorded", ~0-token payload, no header token
counts, dead Copy Block/Copy Turn — and turn numbering disagrees between the run table
(0-based), the URL (0-based), and the Sessions composition chart (1-based).

## Background and goal

The 2026-09-30 web dashboard audit (kyberdash 0.1.7-rc.15, live `~/.kyberdash/canon.db`,
dashboard at :4747) recorded the symptom; audit only, not fixed. Investigation by the
conductor (CodeGraph MCP + direct reads) was re-verified for this plan by direct reads of
every cited file:line in this checkout (self-gathered spot checks; CodeGraph and docs MCP
tools were not available in the authoring harness, so line numbers below were confirmed
against the tree, with two path corrections noted).

Goal: one turn-numbering convention end to end, a resolver that fails loudly instead of
rendering a plausible-but-empty neighbor turn, and an inspector header that reports the
measured token figures it already has.

## Root cause (two coupled defects)

### 1. Mixed 0-based / 1-based turn numbering

- The engine contract is 1-based: `TurnPressure.index` is `index: position + 1`
  (`dash/src/analysis/context.ts:444`), documented as "1-based position of the turn in the
  session" (`dash/src/analysis/context.ts:185`). The session payload serves this verbatim as
  `context` (`contextShape`, `dash/src/canon/sessions.ts:472`, served at `:523`).
- The payload's `turns[]` array is 0-based: `turns: turnRecords.map((record, index) => ({ index, ...`
  (`dash/src/canon/sessions.ts:537-538`).
- The composition chart renders 1-based: `const idx = t.index ?? t.turn ?? i + 1` with label
  `Turn #${idx}` (`dash/web/src/components/SessionSpendCharts.tsx:337`, `:365-367`); first/last
  fallback `context.first.turn || 1` (`:389-390`); heatmap row click passes `row.turnIndex`
  (1-based engine value) (`:1242`); legend click passes
  `selectedTurnIndex ?? rows[0]?.turnIndex ?? 1` (`:1185`, `:1189`).
- The run table displays 0-based `#{turn.turnIndex}` (`dash/web/src/pages/RunDetail.tsx:439-440`)
  with a synthesized 0-based fallback (`Array.from({length: turnCount}, (_, turnIndex) => ({ turnIndex, ...`
  `RunDetail.tsx:186-187`) and drills via `handleOpenTurn(turn.turnIndex)` (`:214-215`).
- The URL `/session/:sessionId/turn/:turnIndex` is a raw 0-based passthrough
  (`dash/web/src/lib/router.ts:112-116` parse — rejects negatives; `:173-180` serialize), and
  `router.test.ts:35` pins an example location with `turnIndex: 3`.

Net effect: "Turn #5" in the chart (the 5th turn) navigates to `/turn/5`, which the content
route reads as the 6th turn (0-based) — off by one.

### 2. The server resolver papers over the ambiguity with a triple fallback

`assembleTurnContent` (`dash/src/server/bridge.ts:1048-1101`) resolves the turn three ways,
each with the same shape: `find((t, i) => t.index === turnIndex || i === turnIndex) ??
(turnIndex >= 1 && turnIndex <= len ? turns[turnIndex - 1] : undefined)` — payload branch
(`bridge.ts:1067-1069`), canonical-records branch (`:1083-1084`), DB-rows branch (`:1096-1098`).
With mixed 0/1-based callers, `t.index === 5` matches the 6th turn while `turns[5 - 1]` is the
5th; which one wins depends on branch order, so the inspector can land on a neighboring span.
When the resolved span has no structured parts (`loadContentRecords(sessionId, targetSpanId)`
returns records with empty `parts`), `rawParts` is `[]` (`bridge.ts:1113`), all five canonical
blocks get `text: ''` and `tokens: undefined` (`reduce(...) || undefined`, `bridge.ts:1245`),
and `assembledText` is `''` (`:1274`). The UI then shows exactly the audit's symptom:

- BlockRail "n/a" badge (`ContextInspector.tsx:182-184`) and "empty" badge (`:194`).
- ContentPane "No content recorded for this block." (`ContextInspector.tsx:318-323`).
- Header shows only `Turn {turnData.turnIndex}` + model, never token counts
  (`ContextInspector.tsx:534-541`) — a secondary gap: measured input/output/fresh/cache_read
  figures already exist on `KyberSessionTurnRow` (`dash/web/src/lib/kyberApi.ts:193`,
  fields `:198-202`).
- Both copy buttons disabled: `disabled={!blockCopyText || ...}` and
  `disabled={!turnData.assembledText}` (`ContextInspector.tsx:546-571`).

Display inconsistency in a third surface: `TurnDetail.tsx:88` renders `Turn {turnIndex}` raw
(0-based) while `TurnAlignedDiff.tsx:127` renders `Turn {turn.turnIndex + 1}` (assumes 0-based)
— actual path `dash/web/src/components/analysis/TurnAlignedDiff.tsx` (corrected from the audit
citation). The client drawer lookup `openDrawerForTurn` uses a four-way fallback
(`t.index === n || t.turn === n || i === n || i + 1 === n`,
`dash/web/src/components/AgentSessionDashboard.tsx:477-483`; corrected path), masking the same
ambiguity client-side. Legacy rows may carry 1-based `turn` instead of `index` — a defensive
read, not emitted by the current writer (`kyberApi.ts:204-205`).

## Live evidence (read-only repro, 2026-09-30, implementation stage)

Dashboard `http://127.0.0.1:4747` against the live store (no writes to `~/.kyberdash`).
Session `claude-desktop:eba7886b-a670-4a96-bf67-f37c86442875` (claude-desktop, 23 turns):

- `GET /api/kyber/session/<id>/turn/{0,1,2,4,5,6,22}/content` → HTTP 200, each with its
  own correct sequential span (`synth:<session>:<uuid>`), correct model
  (`claude-sonnet-5-5`), but `parts: []`, `assembledText: ''`, all five blocks empty
  (`system_prompt`/`tool_definitions` carry the honest harness `notMeasurable` reasons).
- Session payload confirms the numbering split live: `turns[].index` is 0-based
  (`index: 0, 1, 2, ...`) while `context.turns[].index` is 1-based (`first idx: 1`,
  23 turns) — and turn rows carry measured figures (`input: 66022, output: 386,
  fresh: 2, cache_read: 42378`), so Q3 (a) header counts are served data, not estimates.
- Out-of-range probe: `/turn/23/content` → HTTP 200 (the `turns[23-1]` 1-based fallback
  silently serves the last turn, index 22); `/turn/99/content` → HTTP 404.

Verdict: **(b) genuinely missing parts** for this harness's `synth:` spans — consecutive
turns resolve to the correct distinct spans yet all carry zero parts, so no neighbor
mis-resolution explains the emptiness here. The (a) off-by-one hazard is separately real:
the chart's 1-based "Turn #5" navigates to 0-based `/turn/5` (verified in code), and the
live `/turn/23 → 200` probe proves the resolver serves a plausible neighbor instead of
404ing. Per the stage-2 conditions this PR therefore ships the honest empty state, the
numbering convention, and the header token counts — and fabricates no content. The
why-do-`synth:`-spans-carry-no-parts data-capture gap is filed as follow-up issue
[#216](https://github.com/dpalfery/kyber-weave/issues/216) with this evidence.

## Smallest change

1. **One convention (0-based transport):** URL, router, run table, and drawer all carry 0-based
   `turnIndex` (matches payload `turns[].index` and the router passthrough). The composition
   chart converts 1-based engine `TurnPressure.index` to 0-based at the single boundary:
   `onSelectTurn(row.turnIndex - 1, ...)` in `ContextCompositionChart`
   (`SessionSpendCharts.tsx:1242`) plus the `:1185`/`:1189` legend fallback (`- 1`).
2. **All human displays render 1-based:** run table `Turn #${turn.turnIndex + 1}` (keep
   `handleOpenTurn` passing raw 0-based), `TurnDetail` H2 `Turn {turnIndex + 1}`,
   `ContextInspector` header shows the 1-based number. `TurnAlignedDiff.tsx:127` already adds 1
   and becomes correct unchanged.
3. **Strict resolver:** once callers are normalized, drop the 1-based `turns[turnIndex - 1]`
   fallbacks in `assembleTurnContent` (all three branches, `bridge.ts:1067-1098`). Resolution is
   0-based payload `index`, positional `i`, or legacy 1-based `turn` matched as `turn - 1`;
   a wrong index returns 404 loudly instead of a neighboring span. Same strictness for
   `openDrawerForTurn` (drop the `i + 1 === n` branch).
4. **Header token counts:** render the measured per-turn input/output/fresh/cache_read figures
   from the session turns row (`kyberApi.ts:198-202`); when absent, show the honest
   not-measured treatment, never an estimate. Copy buttons' disabled state stays truthful.
5. **Diagnosable empty state:** ContentPane distinguishes "this harness recorded no content for
   this turn (spanId, 0-based turnIndex shown)" from "no such turn in this session" (404).

## Risks and out of scope

- **Live-DB-only symptom:** the audit used `~/.kyberdash/canon.db`; empty blocks can also
  occur legitimately when a harness genuinely captured no parts for a span. T1/T9 fixtures must
  distinguish off-by-one resolution from genuinely-missing parts; the empty-state copy (T10)
  must not claim a defect when the data is simply absent.
- **Legacy rows:** the triple fallback is load-bearing for rows carrying 1-based `turn`
  (`kyberApi.ts:204-205`, `KyberSessionTurnRow`). Strictness must preserve those reads as
  `turn - 1`, not delete them.
- **1-based engine values consumed elsewhere:** `flaggedTurns` and `context.first/last.turn`
  are 1-based engine values the charts consume — do not "fix" the engine side (Q2).
- **URL stability:** router tests and any external links pin 0-based URLs; changing the URL
  scheme is out of scope (Q1).
- **Out of scope:** harness content-capture gaps (why some spans have no parts is a data
  problem to surface honestly, not fabricate); estimating token figures from text (Q3).
