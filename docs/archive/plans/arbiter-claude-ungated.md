# The global Arbiter hook gates Claude Code when no project hook does

**Status: Archived — complete 2026-11-11.** Approved for execution under decision AP1 (autonomous approval of gate `approve-and-execute`). The task file was removed at archival; the decisions, tasks and test contract above are the record.
**Development mode:** `test-first` (RED by `test-dev`, GREEN by `csharp-dev`, never the same worker).
**Autonomy:** `autonomous` (every open item decided by recommendation; provenance in `## Decisions`).
**Scale:** `extends-component`, components `KyberArbiter` (the hook host, its doctor and status) and `KyberSquad` (the Claude hook block in the shared settings file).
**Delivery:** one bug-fix pull request on branch `claude/fix/arbiter-claude-ungated`, base `origin/main` at `00e2594b`.

**Bottom line.** The Arbiter (the hook that gates agent dispatches) gates nothing for Claude Code in a project that turns it on but has no project Claude hook: the user-level hook hands the dispatch to a project hook that does not exist. After this change the user-level hook evaluates the dispatch under the project's configuration unless the project opts out or a project hook really covers it; one dispatch is never evaluated twice; `arbiter doctor` and `arbiter status` say per harness what gates it; and the Claude settings block is always written with Claude's documented `PreToolUse` / `PostToolUse` names.

## Problem and goal

**Problem.** Reproduced in this worktree:

1. `kyber-weave-arbiter hook --harness claude --scope global` fed a `PreToolUse` `Agent` payload whose `cwd` is a project with `arbiter.enabled: true` prints `Arbiter global scope: deferred-to-project.` and exits 0 with no decision. `HookCommand.Run` calls `IsGlobalScopeProjectDefer`, which defers whenever the project config has `arbiter.enabled` true or explicitly false. The same payload at project scope evaluates and denies, so the engine works.
2. This repository has no project Claude hook (tracked `.claude/settings.json` holds only `SessionStart`; no `.claude/agents/`), and the owner's user-level agents and conductor skill carry none. The only Claude hook that fires is the user-level one, so it defers to nothing: about 30 dispatches in a real run recorded zero decisions.
3. `kyber-weave arbiter doctor` prints `ok Project hooks: installed.` anyway, because `ArbiterDoctorCommand.HasProjectHooksInstalled` returns true when any harness has a project deployment or any receipt block has a target.
4. The user-level `~/.claude/settings.json` holds `PreToolUse` and a lower-case `postToolUse`. `SquadHookJsonBlock.CursorArrays`, used for both the Cursor and Claude formats, picks the lower-case container unless the PascalCase key already exists. Claude Code documents only PascalCase event names.
5. `~/.kyber-weave/kyber-weave.yml` lists `arbiter.global.targets: antigravity, copilot` but the global Squad receipt owns a `claude` block in `settings.json`. `ArbiterHookRefresher` picks global targets from that list, so `kyber-weave update` never refreshes the Claude block.

**Goal.**

1. The user-level hook evaluates a Claude dispatch under the project's configuration whenever no project hook covers it. It still defers when the project sets `arbiter.enabled: false`, or when a project hook covers the dispatch.
2. No dispatch is evaluated twice by the project hook and the user-level hook together.
3. `arbiter doctor` and `arbiter status` report, per installed harness, whether a project hook gates it, the user-level hook gates it under the project's configuration, or nothing does, with the exact fix command; and they flag a global receipt block whose harness is missing from `arbiter.global.targets`.
4. The Claude settings block is written only under `PreToolUse` / `PostToolUse`; a legacy lower-case Squad entry is migrated on the next render; Cursor is unchanged.

| D4 | How is one dispatch never evaluated twice? | A per-dispatch claim, only on dispatch events (tool `Agent` or `Task`, events `PreToolUse` and `PostToolUse`); Read-guard and hand-back events never claim. A user-level `CreateNew` that loses the race defers the same way. When the payload has no `tool_use_id`, candidates mean defer (logged, naming them) and none mean evaluate. Each claim write deletes claim files older than 24 hours in that folder. | A static probe alone cannot answer "covered": skill hooks register only when the skill is invoked, and whether an agent file's hooks are active under `--agent` is not documented (D13). Claude Code runs matching hooks in parallel and de-duplicates identical handlers only across settings files, and the user-level command differs anyway (`--scope global`). Every captured Claude fixture carries `tool_use_id`. Rejected: static rule only (leaves either a double evaluation or an ungated main thread); always evaluate in the user-level hook (double evaluation wherever a project hook exists). | ANSWERED: autonomous, low-confidence, no authoritative source. ## Investigation findings

Read at `claude/fix/arbiter-claude-ungated`, revision `00e2594b`, through the worktree's own CodeGraph index (`codegraph explore` in `/Users/dave/git/claude-worktree/kyber-weave/inspiring-jemison-edd4bd`).

- **Deferral.** `HookCommand.Run` (`src/KyberWeave.Arbiter/Hooks/HookCommand.cs`) calls `IsGlobalScopeProjectDefer(repoRoot)` under `HookScope.Global`; it returns true when the project config has `Arbiter.Enabled` or `Arbiter.ExplicitlyEnabled == false`, logs `Arbiter global scope: deferred-to-project.` and returns. - **Ledger directory.** `ArbiterHookDecisionEngine.ResolveArbiterDirectory` (`src/KyberWeave.Arbiter/Hooks/ArbiterHookDecisionEngine.cs`) returns `~/.kyber-weave/arbiter/projects/<sha256 of root>` for `HookScope.Global`, else `<root>/artifacts/arbiter`. `HookContext.Scope` has no other use in the host. The CLI's `ArbiterCommandComposition.ResolveArbiterDirectory`, used by `audit` and `tune`, reads only `<root>/artifacts/arbiter`.
- **Adapter seam.** `IHarnessHookAdapter` (`src/KyberWeave.Arbiter/Hooks/IHarnessHookAdapter.cs`) already has default members (`AnswerWithoutConfig`, `DisabledAllowDocument`); `ClaudeHookAdapter` (`src/KyberWeave.Arbiter/Hooks/Adapters/ClaudeHookAdapter.cs`) is registered once, for token `claude`, in `CommandHookAdapters`. `ClaudeHookAdapter.ResolveCaller` reads `agent_type` before `--caller`.

## Risks

- **A main-thread wait.** Only when an effective project skill carries the dispatch hook and was not invoked; bounded at 1.5 s per dispatch and logged.
- **A lost race.** If the project hook starts more than 1.5 s after the user-level hook, the user-level hook evaluates without the caller name the project hook would have had; still one evaluation.
- **Claims folder growth.** Pruned at 24 hours on every claim write.
- **Undocumented Claude semantics.** `agent_type` presence and skill hooks inside sub-agents are not fully documented (D13); D4 makes the design hold either way.
- **Doctor regressions.** The old `installed` line is gone; scripts that grep for it break, which is the intent.
- **Owner machine.** Nothing changes there until the owner updates and runs D11's command.

## Out of scope

- A per-dispatch probe for any harness other than Claude (follow-up; D7).
- Making `kyber-weave update`'s refresher select global targets from the receipt rather than `arbiter.global.targets` (follow-up; doctor now flags the mismatch).
- Any change to the project-scope renderers, the entry-point skill, or the rules and engine.
- Doctor flagging a lower-case Claude container directly (it shows up as `ungated`, D8).
- Re-rendering the owner's real global hooks.
