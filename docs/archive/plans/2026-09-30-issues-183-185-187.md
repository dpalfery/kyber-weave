## Background and goal

The audit's headline: the same session shows 1.9M input / 94% cache in one view and
dashes/zeros in another. Goal: every served payload carries the measured figures its view
needs, each figure has one derivation point, and absence renders as explicit
not-measured — never as '—' where data exists, and never as zero.

## Shared root cause and the honest-unobservability rule

Each defect is the same pattern: a payload contract drops a measured figure the view
needs, and the view renders absence as '—' or 0.0% while a sibling view that computes
from raw rows shows the real number. The fix family, applied three times:

1. carry the measured figure through the payload contract,
2. compute it honestly at one derivation point,
3. never present absence — or an estimate — as a measured zero.

**Honest-unobservability rule** (applies to every task below): a figure the source did
not measure is rendered as an explicit not-measured treatment, never as zero or an
estimate dressed as measured. Precedents already in the tree: the `findingCount` join
comment — "a fabricated zero sitting directly beneath a findings panel listing the same
runs' findings" (`dash/src/server/routes.ts:547-553`); "a not_measurable total is an
object, not a number, and must not be coerced into the denominator"
(`dash/src/canon/harnesses.ts:141-143`); and the engine's own residual semantics — "a
measured-only turn's gap is content the source never exported, which is a different
fact" (`dash/src/analysis/context.ts:203-207`). This PR's three violations: "Residual:
0.0%" for 66.5K unattributed tokens (#187), "on 0 turns" beside 10.8M of cache creation
(#185), and '—' beside measured per-turn figures (#183).

## Issue #183 — run detail turn table empty, scorecard falsely UNMEASURED, doubled run ids

### Root cause (evidence)

- `GET /api/kyber/run/:id` returns `{ run, executionTree, executions, findings }` — no
  `turns`, no `scorecard` (`dash/src/server/routes.ts:563-590`).
- `RunRow` has `executionCount` but no `turnCount`/`totalInput`/`totalOutput`/`costUsd`/
  `scorecard`/`turns` (`dash/src/canon/types.ts:297-309`); `ExecutionRow` has no
  `turnCount`/`costUsd` (`dash/src/canon/types.ts:312-324`). The web contract already
  promises all of it: `KyberRunSummary` declares `turnCount`/`totalInput`/`totalOutput`/
  `costUsd`/`scorecard` (`dash/web/src/lib/kyberApi.ts:546-568`) and
  `KyberExecutionSummary` declares `turnCount`/`costUsd` (`:591-593`) — the contract
  promises what the engine never sends.
- `KyberRunTurn` exists and `KyberRunDetail.turns` is optional
  (`dash/web/src/lib/kyberApi.ts:598-623`), but `fetchRun` never populates it
  (`:634-648`).
- `RunDetail` therefore synthesizes stub rows `{ turnIndex, executionId, sessionId }`
  from the execution session's `turnCount` (`dash/web/src/pages/RunDetail.tsx:158-193`)
  — stubs carry no model/tokens/pressure/cache/cost, so the table renders '—' in every
  measured column (`RunDetail.tsx:426-470`); the scorecard fallback is all
  not_measurable with `secondaryCost` not_measurable (`RunDetail.tsx:196-213`). Harness
  Recent Runs shows the same absence: `r.turnCount ?? '—'` and the costUsd dash
  (`dash/web/src/pages/HarnessDetail.tsx:375`, `:391-393`, "Decision D9: Secondary
  derived cost").
- The scorecard's unmeasured reason is false: "Telemetry missing: harness does not
  export cache read/creation counters" originates in the engine's
  `UNMEASURED_REASONS.cacheEfficiency` (`dash/src/analysis/scorecard.ts:49`) and is
  surfaced verbatim (`dash/web/src/components/analysis/Scorecard.tsx:38`,
  `pages/HarnessDetail.tsx:117`) — false for claude-desktop, whose session payloads
  carry per-turn `cache_read`/`cache_creation` (`dash/src/canon/sessions.ts:543-544`).
- The measured data already exists server-side: session payload `turns[]` carry `index`
  (0-based), `spanId`, `timestamp`, `model`, `input`, `output`, `fresh`, `cache_read`,
  `cache_creation`, `reasoning` (`dash/src/canon/sessions.ts:537-548`); context turns
  carry `pressure` (`dash/src/analysis/context.ts:184-226`); the summary carries `cost`
  (`sessions.ts:509-519`). Nothing needs re-parsing — only carried through.
- Doubled ids: `identities.claim` returns a harness-qualified id
  (`dash/src/canon/measurability.ts:285-293`, `` `${canonical}:${key}` ``), candidates
  set `executionId: sessionId` from it (`dash/src/canon/runs.ts:422-426`), and the
  session_fallback composition sites then prefix the harness again:
  `derived:${harness}:${cand.executionId}` → `derived:claude-desktop:claude-desktop:<id>`
  (`runs.ts:152`, `:510`, `:616`). The clean-cwd sites (`:141`, `:566`, `:593`) are
  unaffected.

### Smallest change

1. **Serve-time enrichment, one derivation point.** `KyberBridge` gains
   `runMeasuredFigures(runId)` — join `listExecutions(runId)` → `sessionId` →
   `store.getSessionPayload` summaries — returning measured-only
   `{ turnCount, totalInput, totalOutput, costUsd }` (absent figures omitted, never 0;
   `costUsd` = sum of session cost totals only when priced). It feeds both the runs list
   and the run-detail `run` object. `RunRow`'s stored shape is unchanged — no schema
   change, no migration, figures always live.
2. **`getRunTurns(runId)`:** per execution → session payload → `turns[]` mapped to run
   turn rows `{ turnIndex (0-based, #184 transport convention), executionId, sessionId,
   model, inputTokens, outputTokens, tokens (in+out when both measured), cacheHitRatio
   (cache_read ÷ input when input > 0), contextPressure (context.turns joined by array
   position — engine context index is 1-based, so join positionally, never by index
   equality; omit on mismatch), costUsd (per Q3), timestamp }`. Unmeasured fields are
   omitted — never 0.
3. **`getRunScorecard(runId)` (per Q2):** recommended run-scoped digest reusing the
   harness rollup machinery (`digestSessions`, `dash/src/canon/harnesses.ts:140-146`;
   dimension derivation, `dash/src/analysis/scorecard.ts`) over the run's sessions, with
   run-scoped measurability reasons that never claim the harness lacks telemetry it
   exported.
4. **Route** (`routes.ts:563-590`) spreads `turns`, `scorecard`, and the enriched `run`
   into the payload.
5. **Web:** `fetchRun` populates `turns` (`kyberApi.ts:634-648`); `RunDetail` already
   prefers `run.turns` (`:166-170`) and `run.scorecard` (`:196-198`), so the table and
   scorecard light up; the client fallback's reason text becomes a true statement ("no
   served run scorecard for this run"), never the false harness-telemetry claim.
   HarnessDetail Recent Rows lights up from the served `turnCount`/`costUsd` with no
   view change.
6. **Id normalization:** a helper strips one leading `${harness}:` from the seed before
   composing `derived:` ids at `runs.ts:152`, `:510`, `:616`. `buildRuns` already drops
   stale rows on rebuild (`runs.ts:392-397`, `:656-663`), so doubled rows disappear on
   the next projection — no data migration.

`dash/src/server/kyber-api.test.ts` (exists; boots the real dashboard server over a

### Issue risks

- Multi-execution runs: `turnIndex` is 0-based per execution, so rows from different
  executions repeat indices by design; the table already filters by `executionId`
  (`RunDetail.tsx:166-170`) — the fixture must cover a two-execution run to pin this.
- Id normalization changes derived run ids; anything bookmarking a doubled id breaks.
  Acceptable (derived ids, ADR 0008/D13); the rebuild-prune test guards orphans.
- A run-scoped scorecard must not reuse harness-level availability claims verbatim
  (`harnessDimensionAvailability`) where the run's own sessions did export the
  telemetry — that false claim is the bug being fixed.

## Issue #185 — Sessions cache hit ratio tile always '—'

### Root cause (evidence)

- `buildSessionRow`'s summary emits `turn_count, request_count, total_input,
  total_output, total_cache_read, total_cache_creation, duration_ms, models, cost` —
  never `cache_hit_ratio` or `cache_creation_coverage`
  (`dash/src/canon/sessions.ts:509-519`); a sweep of `dash/src` confirms zero writers of
  either key outside tests.
- The web contract already declares both optional (`SessionSummaryPayload`,
  `dash/web/src/lib/kyberApi.ts:54-80`) — again promising what the engine never sends.
  Consumers: the Cache Read sublabel needs `u.cache_hit_ratio`
  (`dash/web/src/components/AgentSessionDashboard.tsx:878`); the Cache Creation sublabel
  renders `on ${u.cache_creation_coverage ?? 0} turns` — literally "on 0 turns"
  (`:888-892`); the Cache Hit Ratio tile renders `'—'` because the field is always
  absent (`:946-952`, footnote "cache_read ÷ input").
- Sibling views that compute honestly show values: the chart's
  `cacheHitPercent` from turn rows → "Cache Hit: 94.0%"
  (`dash/web/src/components/SessionSpendCharts.tsx:505`);
  `SessionCostPanel` computes the ratio from summary totals and "never fabricates 0% if
  unmeasured" (`dash/web/src/components/SessionCostPanel.tsx:234-242`); the harness
  rollup computes the rate from measured totals with a not-measurable answer otherwise
  (`dash/src/canon/harnesses.ts:140-146`, `:265-284`).

### Smallest change (per Q1 — recommended: single writer)

Emit both fields from `buildSessionRow` (`sessions.ts:509-519`):
`cache_hit_ratio = total_cache_read / total_input` when both are measured numbers and
`total_input > 0` — omitted (never 0) otherwise, matching the tile's declared formula
and the harness rollup; `cache_creation_coverage` = count of `turns[]` with
`cache_creation > 0` (the chart's own `ccTurnCount` semantics,
`SessionSpendCharts.tsx:502-503`), omitted when there are no turn rows. One writer keeps
the tile, `SessionCostPanel`'s preference path, and every future view consistent; the
existing view-side fallbacks stay as belt-and-braces only where they already exist
(`SessionCostPanel.tsx:234-242`). The only view change: the `?? 0` at
`AgentSessionDashboard.tsx:891` becomes honest absence (omit the count rather than
print "on 0 turns") so legacy payloads without the field cannot fabricate a zero.

### First failing test (RED)

`dash/src/canon/sessions.test.ts` (exists) — new case **"summary emits measured
cache_hit_ratio and cache_creation_coverage"**: fixture session with
`total_input` 1,900,000, `total_cache_read` 1,786,000, and 2 of 3 turns with
`cache_creation > 0` → `summary.cache_hit_ratio ≈ 0.94` and
`summary.cache_creation_coverage === 2`; a session with no measurable input omits both
keys (asserts absence, not 0).

### Issue risks

- Denominator honesty: the chart uses `inputSum = fresh + cacheRead + cacheCreation`
  (`SessionSpendCharts.tsx:504-505`); the tile/rollup use `total_input`. They agree when
  input is the sum of its parts (the measured case here) but may legitimately differ
  otherwise — the test fixture pins the agreeing case; do not force-align the chart in
  this PR.
- Legacy DB sessions lack the fields until the session projection rebuilds (a rebuild is
  authoritative, `sessions.ts:316-317`); until then tiles render the honest '—'.

## Issue #187 — Context Composition "Residual: 0.0%" beside 66.5K unattributed tokens

### Root cause (evidence)

- The engine computes it correctly: `residual = turn.inputTokens - bucketedTokens`
  (`dash/src/analysis/context.ts:414`), with honest attribution semantics
  (`:203-207`). But `TurnPressure` carries no input/reported-input field
  (`context.ts:184-226`), and `serializeContext` spreads the turn as-is — the measured
  per-turn input never reaches the wire (`dash/src/canon/sessions.ts:626-633`).
- The web type documents the gap: `KyberContextTurn.reported_input` is "read
  defensively … though the engine's TurnPressure does not carry one"
  (`dash/web/src/lib/kyberApi.ts:244-247`) — i.e. always absent.
- So `extractNormalizedContextTurns` computes `reported = t.reported_input ??
  t.bucketedTokens ?? fallbackReported` (`dash/web/src/components/SessionSpendCharts.tsx:~341`)
  — `bucketedTokens` (124) always wins; `normalizeContextBuckets` starts residual at 0
  (engine buckets carry no residual key) then `max(0, reported − known) = max(0, 0) = 0`
  (`:306-316`). The engine's `residual.tokens` (~66.5K, read into `residualTokens` at
  `:339`) is used only for `fallbackReported` and discarded. Aggregate
  `avgResidualPct = totalResidual / totalAllTokens` (`:1118-1121`) renders "Residual:
  0.0%" (`:1211-1212`) while turn 1's 66.6K input sits 99.8% unattributed. Absence
  presented as measured zero.

### Smallest change (per Q4 — recommended: `reported_input` key)

1. `serializeContext` emits `reported_input: turn.inputTokens` on each serialized
   context turn (`sessions.ts:626-633`) — the exact key the web already reads and the
   type already declares; update the stale comment at `kyberApi.ts:244-247`.
2. `extractNormalizedContextTurns` prefers the measured input:
   `reported = t.reported_input ?? (known + engineResidual when > 0) ?? t.bucketedTokens`,
   and seeds the residual bucket from the engine's `residual.tokens` so
   `residual = max(engineResidual, reported − known)` (`SessionSpendCharts.tsx:306-316`,
   `~333-360`). A fully-bucketed turn still legitimately reports a measured 0.
3. Panel aggregate: `avgResidualPct` is computed only over turns with a measured input
   basis; when none exists, the header renders an explicit not-measurable treatment
   ("Residual: not measurable") instead of "0.0%" (`:1118-1121`, `:1211-1212`).

### First failing test (RED)

`dash/src/canon/sessions.test.ts` — new case **"serialized context turns carry the
measured reported_input"**: fixture turn with input 66,600 →
`payload.context.turns[0].reported_input === 66_600`. Then
`dash/web/src/components/SessionSpendCharts.test.tsx` (exists; composition suite) — new
case **"residual reflects measured input"**: a turn with `reported_input: 66_600` and
buckets summing 124 → residual segment ≈ 66,476 and the header renders
"Residual: 99.8%", not "0.0%"; plus a context with no measured input anywhere asserting
the not-measurable treatment rather than "0.0%".

### Issue risks

- Over-correction: a turn whose input is fully bucketed has a measured residual of 0 —
  it must still render 0.0%; not-measurable applies only when no measured input basis
  exists. The GREEN tests cover both.
- The `KyberContextTurn.reported_input` field stays optional — legacy payloads without
  it take the engine-residual fallback, never a silent zero.

## Risks and out of scope

- **Honesty is the acceptance bar:** every new figure is measured or explicitly absent.
  A test that reaches green by emitting 0 (or an estimate) for unmeasured data fails
  review; the honest-unobservability precedents cited above are the standard.
- **Shared denominators:** #185's ratio (`total_input`) and the chart's `inputSum` agree
  only when input is the sum of its parts; do not force-align the chart in this PR.
- **Positional joins:** run-turn pressure joins context turns by array position (1-based
  engine index vs 0-based payload index); mismatch omits the figure rather than guessing.
- **Derived id churn** (#183) breaks doubled-id bookmarks; acceptable for derived ids,
  guarded by the prune assertions.
- **Out of scope:** harness content-capture gaps (issue #216); changing the engine's
  1-based context-turn contract (#184 settled display vs transport); URL schemes;
  per-request cost attribution; the tray UI; rewriting the chart's cache-hit formula.
