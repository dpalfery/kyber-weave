# Make ingest coverage visible and honest — #189, #198, #199

Fixes [issue #189](https://github.com/dpalfery/kyber-weave/issues/189),
[issue #198](https://github.com/dpalfery/kyber-weave/issues/198), and
[issue #199](https://github.com/dpalfery/kyber-weave/issues/199) in one PR.

**Development mode: test-first.** Every task names its failing test first.

## Summary

All three audit findings are one defect seen from three angles: the canonical store
ingests far less than the harness sources hold, and no surface says so. The refresh
window that discards most history (`--history-weeks`, default 2) is persisted nowhere
and mentioned nowhere; the live OTLP collector records its activity nowhere (the
`ingest_log` audit table has exactly one production writer — a manual rebuild tool);
and the split-identity plus checkpoint state that would let a reader see what was
merged, partial, or never covered is invisible outside the CLI refresh table.

This plan does not add parsers and does not widen any window by default. It makes the
coverage contract observable: persist the window per refresh run, record collector
activity, expose per-source counts, checkpoint statuses (including `partial`), and
receiver last-received time through the report and API, group the Claude split
identities at display level only, and give `codeburn/`-namespaced sources honest
display names — unknown stays unknown, never zero.

## Scope

- `dash/src/canon/refresh-run.ts`, `dash/src/canon/store.ts` (migration 14→15),

- `dash/web/src/**` (`pages/ContextDoctor.tsx`, `components/analysis/ScorecardMatrix.tsx`,
  `lib/kyberApi.ts`) — coverage banner, ingest activity panel, grouped matrix rows,
  explicit no-data reasons.
- Docs: `docs/dash/runbook.md`, `docs/dash/architecture.md`, `docs/dash/telemetry-inventory.md`.

## Non-goals

- No new per-harness parsers, no new adapters, no attribution-vote changes (#195's
  antigravity attribution work is untouched).
- No change to `DEFAULT_HISTORY_WEEKS = 2` and no change to the tray's incremental
  `REFRESH_ARGS` (decision D1 below); widening history stays an explicit operator action.
- No persisted identity merge of `claude-cli` / `claude-desktop` / `claude-code`
  (decision D3); split client surfaces stay distinct in `canon.db`.

  `RunDetail.tsx`, or findings code (Group B) except the single additive bridge seam.
- No backfill or fabrication of historical `ingest_log` rows; pre-existing records are
  counted from the `records` table, and "receiver status" is never claimed as running.

## Issue #189 — sessions never reach the dashboard

### Root cause (with evidence)

1. **The ingest window discards older history and the tray always refreshes with the
   default.** `DEFAULT_HISTORY_WEEKS = 2`
   (`dash/src/refresh/orchestrator.ts:39`); the window is
   `[commandStartedAt − N×7 d, commandStartedAt]`
   (`dash/src/refresh/source-reader.ts:89-92`, applied at
   `orchestrator.ts:68-70`). The tray refreshes on a cadence with the bare
   incremental args `["dash", "refresh"]` — deliberately no flag
   (`dash/tray/src-tauri/src/scheduler.rs:26-28`, requirement 10.1) — so every
   cadence run re-covers only the trailing two weeks and sessions older than that are
   never ingested by the tray path. That is the mechanical gap behind
   Codex 647→5, Pi 76→0, KiloCode 70→0.
2. **The window is not persisted, so no surface *can* state it.** `refresh_run`
   records id/started_at/completed_at/status/pid/trigger/summary only
   (`dash/src/canon/refresh-run.ts:54-69`); `startRefreshRun`
   (`dash/src/canon/store.ts`, called at `orchestrator.ts:75-82`) receives no
   window. The report's coverage section surfaces refresh recency
   (`dash/src/analysis/report/build.ts:266-277`, `readRefreshState` at
   `build.ts:300-305` → `bridge.getRefreshState()`, `bridge.ts:1770-1774`) but no
   window, and its remedy hints say only "Run `kyberdash dash refresh`"
   (`build.ts:268,274,276`). The CLI table prints `historyWeeks` in the report
   object (`dash/src/refresh/report.ts:23,54-67`) but the web UI never shows it.
3. **The harness matrix claims "per live harness" while listing every registered or
   observed harness.** `buildHarnessRollup` seeds registered descriptors plus
   observed ids (`dash/src/canon/harnesses.ts:430-432`); zero-data rows do carry an
   honest reason (`harnesses.ts:191-228`, "No collectable runs or sessions
   recorded…"), but `/api/kyber/harnesses` (`dash/src/server/routes.ts:499-512`)
   returns them undifferentiated, and the web matrix caption asserts "Six
   independent dimensions per live harness" (`dash/web/src/components/analysis/ScorecardMatrix.tsx:135`)
   without a no-data state or window disclosure. Hence 41 of 52 rows silently blank.

### Smallest change

- **Persist the window:** migration 14→15 adds `history_weeks INTEGER` to
  `refresh_run` (`SCHEMA_VERSION = 14` today, `dash/src/canon/store.ts:81`);
  `startRefreshRun` takes it; `refreshHarnessSources` passes `historyWeeks`
  (`orchestrator.ts:75-82`). Old rows read as `null` = window unknown, stated as
  such.
- **Surface it:** `getRefreshState()` additionally returns `historyWeeks` (and the
  derived covered-from/through of the last success); `ReportCoverage.refresh`
  (`dash/src/analysis/report/types.ts:108-112`) carries it; text/Markdown renderers
  print "Coverage window: last N weeks (<from> → <through>)"; when the scoped window
  holds no session, the hint names the widening command
  (`kyberdash dash refresh --history-weeks <n>`), not just the bare command.
- **Differentiate the matrix:** `/api/kyber/harnesses` rows gain
  `family` (D3), `noDataReason` (from the rollup payload reason), and a checkpoint
  summary (`ok/partial/failed/unavailable` counts per harness, from
  `source_checkpoint` via the T4 seam). `ContextDoctor.tsx` renders a coverage banner
  (window + counts of harnesses with no in-window data) and groups zero-data rows
  under an explicit "no records in coverage window" state instead of a dash-filled row.

### Not changing

- `DEFAULT_HISTORY_WEEKS`, tray `REFRESH_ARGS`, scheduler cadence, checkpoint reuse
  semantics (`recordsForUncoveredCommit`, `orchestrator.ts:459-482` — widening
  remains incremental), and no new parsers. The doctor-vs-dashboard delta itself
  (source-store counts) stays in `kyberdash doctor`; the dashboard only ever states
  what its own coverage window explains.

## Issue #198 — OTLP collector activity invisible and partly unattributed

### Root cause (with evidence)

1. **Nothing in the live ingest path writes `ingest_log`.** The audit table exists
   (`dash/src/canon/store.ts:225-230`) with `logIngest` /
   `getIngestLog` (`store.ts:2404-2421`), but its only production caller is the
   manual rebuild tool `reingestFromExports` → `store.logIngest(INGEST_SOURCE…)`
   (`dash/src/tools/reingest.ts:80`, source label `span-exports`). The live
   collector's span sink `upsertMany` calls `ingestBatch` and then writes only a
   `console.log` line (`dash/src/otel/service.ts:123-143`); `ingestBatch` itself
   never logs (`dash/src/canon/ingest.ts:115-173`). So the collector's only activity
   record is stdout of a background process.
2. **The one consumer of `ingest_log` therefore always shows nothing.**
   `getMeta()` builds `sources: [{origin, seen, new}]` from
   `SELECT … FROM ingest_log GROUP BY source`
   (`dash/src/server/bridge.ts:2271-2289`) — an empty table yields `[]`, and the
   payload carries no last-received time in any case. No route exposes receiver
   status (`dash/src/server/routes.ts` has none; the receiver is a separate
   process, `dash/src/cli/register.ts:79-89`), and the web UI has no ingest panel.
3. **Attribution residue is unexplained anywhere a user can see.** The live pipeline
   attributes by fingerprint vote and quarantines the unclaimed remainder with
   reasons `unclaimed` / `non-model span` (`ingest.ts:124-133,147-153`); the
   deprecated pre-pipeline path stamped `harness: 'unattributed'`
   (`dash/src/otel/service.ts:40-52`), which is where stored `unattributed` rows
   come from. Quarantine rows are countable (`bridge.ts:2224-2231`, report
   `quarantineCount`, `build.ts:279`) but per-reason and per-source breakdowns are
   surfaced nowhere.

### Smallest change

- **Record activity at the sink:** in `otel/service.ts`, `upsertMany` writes one
  `logIngest(source, count)` row per distinct span source in the decoded batch
  (source = `service.name`, `'otlp'` when unnamed — `ingest.ts:55,63-74`), and
  `upsertLogs` writes one `otlp:logs` row sized to the batch, so last-received
  reflects any receiver request (D4). Written after `ingestBatch` returns, on the
  store the writer already owns; no schema change.
- **Derive per-source counts from data, not from the log:** the read seam (T4)
  exposes `getIngestActivity()` = per-source record counts from
  `records GROUP BY source` (true for history, including legacy `unattributed` and
  `codeburn/*` rows) joined with `ingest_log` sums and `MAX(timestamp)` as
  `lastReceivedAt`. Empty log + empty table ⇒ `{ status: 'unknown' }` with the
  reason "no receiver activity recorded" — never `0`, never "running".
- **Surface:** `/api/kyber/coverage` (new route in `routes.ts`) returns refresh
  window (T2), ingest activity, per-reason quarantine counts, and checkpoint
  statuses; `ContextDoctor.tsx` renders an "Ingest" panel from it: per-source counts
  with display names (T6), last-received line ("last received <t> (<n> ago)" /
  "no receiver activity recorded — receiver status is not observable from this
  page"), and quarantine reasons with counts.

### Not changing

- No new adapters, no relaxation of the fingerprint vote, no re-attribution of the
  138 legacy `unattributed` rows (that is #184/#195 territory), no backfilled
  `ingest_log` history, and no claim of receiver liveness — a separate process's
  status is honestly reported as unobservable from the web server.

## Issue #199 — unmerged sources, hidden partial checkpoints, `codeburn/` names

### Root cause (with evidence)

1. **Three Claude rows are three persisted identities, by design, with no
   display-level grouping.** File-sourced records carry
   `source = 'codeburn/<provider>'` (`FILE_SOURCE_PREFIX`,
   `dash/src/canon/measurability.ts:67-73`), and the refresh registry deliberately
   splits Claude into `claude-cli` / `claude-desktop` / `claude-unclassified`
   (`dash/src/refresh/registry.ts:41`; "split client surfaces stay distinct",
   `measurability.ts:171-178`). OTLP-side Claude spans are claimed by
   `claudeCodeAdapter` → harness `claude-code` (`dash/src/canon/ingest.ts:39-45,136-157`).
   Record-level dedup across the two paths exists
   (`orchestrator.ts:290-294,518-545`), but nothing folds the three ids into one
   family for display: `SURVEY_FAMILY` already maps all three to `claude-code`
   (`measurability.ts:146-163`) yet is private and used only for E4 survey
   vocabulary. `/api/kyber/harnesses` (`routes.ts:499-512`) and
   `HARNESS_DISPLAY_NAMES` (`dash/web/src/pages/ContextDoctor.tsx:40-64`, which has
   no `claude-cli`/`claude-desktop` entries at all) render them as three unrelated
   rows: `claude-desktop`, `claude-code`, `claude-cli`.
2. **`partial` checkpoints are written but never read by any surface.** The
   orchestrator stamps `source_checkpoint.lastStatus = 'partial'` when a unit had
   problems (`orchestrator.ts:307-313,420-448`) — copilot-cli's 31 partial /
   0-record checkpoints — but the only readers of `listSourceCheckpoints` /
   `getSourceCheckpoint` are the orchestrator itself and tests
   (`dash/src/canon/store.ts:1213,1220`; grep confirms no server or web consumer).
   The CLI prints partial rows to stderr (`dash/src/refresh/report.ts:70-75`); the
   dashboard shows nothing.
3. **Raw source namespaces leak to users.** `codeburn/` is deliberately retained as
   a stored-data namespace — emitters send `codeburn.*` attributes and canon rows
   carry the prefix (`dash/src/branding/user-visible-name.test.ts:29-45` pins this) —
   while user-visible output must not say "codeburn" (`dash/src/identity.test.ts:39,53`).
   Once sources are surfaced at all (T5's counts, #198), they must pass through a
   display-name layer; today no such layer exists for source names, so raw
   `codeburn/claude-desktop` would render verbatim. ADR 0020's severing is otherwise
   complete; this is the residual display seam.

### Smallest change

- **Display-level family only:** export `harnessFamily(harness)` from
  `measurability.ts` (wrapping the existing `SURVEY_FAMILY`/`surveyFamily`,
  `measurability.ts:146-169`); `/api/kyber/harnesses` rows carry `family`; the web
  matrix groups rows by family with per-origin counts and keeps each canonical id
  visible and distinct (D3). No stored id, rollup key, or API filter changes.
- **Surface checkpoints:** the T4 seam exposes
  `getSourceCheckpointStatuses()` (read-only over `listSourceCheckpoints`);
  `/api/kyber/coverage` returns them; `ContextDoctor.tsx` shows per-harness
  checkpoint state including an explicit "N sources partial (problems recorded,
  coverage incomplete)" line and "0 records" where `recordCount = 0`.
- **Source display names:** add `sourceDisplayName(source)` (strip
  `FILE_SOURCE_PREFIX`, label local-file vs OTLP vs legacy-unattributed) used by
  every new surface; the raw value rides along as `rawSource` for auditability.

### Not changing

- No persisted identity merge, no `normalizeHarnessName` edits, no checkpoint
  semantics change (partial stays partial; nothing auto-retries), and the
  `codeburn/` prefix stays in stored data — only its rendering changes.

## Honest-unobservability rule (binding on every task)

Governing rule: [`docs/rules/honest-unobservability.md`](../../rules/honest-unobservability.md).
For this PR specifically:

- **Never invent counts.** A number shown must come from a row that exists:
  `refresh_run`, `ingest_log`, `records`, `source_checkpoint`, or `quarantine`.
  Anything else renders as an explicit unknown with a reason.
- `historyWeeks = null` on pre-migration runs renders "coverage window unknown
  (recorded before window tracking)", not 2 and not 0.
- No `ingest_log` rows ⇒ receiver panel says "no receiver activity recorded";
  receiver liveness is never inferred from recency. Staleness beyond a stated
  threshold is reported as "no activity recorded since <t>", which is a fact about
  the log, not a claim about the process.
- Zero-data harnesses keep their rollup reason verbatim; the matrix never renders
  `0 sessions` where the truth is "none in the coverage window".
- Family grouping sums nothing across origins: per-origin counts stay visible
  beside the family label, so grouping never creates a fabricated aggregate.

## Risks

1. **`bridge.ts` merge conflict with Group A** (T4). Mitigation: one additive
   end-of-class change set, landed early or co-owned; T4 is the only task in that
   file. Severity if it lands badly: rebase noise, not semantic drift.
2. **Schema migration on a 3 GB live store.** `ALTER TABLE … ADD COLUMN` on
   `refresh_run` is O(1) metadata in SQLite and the table is small (one row per
   refresh). Risk is negligible; the migration still runs in one transaction per
   house pattern (`store.ts:286-291`).
3. **`ingest_log` growth from cadence refreshes/collector batches.** Rows are tiny
   and bounded by receiver traffic; accepted for now — flagged as a follow-up if
   the collector writes thousands of rows/day (a rollup in `purgeExpiredContent`
   would be a separate, justified change).
4. **`records GROUP BY source` cost on 3 GB.** One indexed-order scan per coverage
   request; acceptable for a status panel. If slow in practice, execution may cache
   per refresh run — note it, do not silently drop the count.
5. **Snapshot churn** from hint/renderer text changes (T3) — updates must be
   reviewed line-by-line, never `-U` blindly.
6. **Family grouping misread as a merge.** Mitigated by per-origin counts beside
   every family label and unchanged API filters; tests pin both.
