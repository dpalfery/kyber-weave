# Validate specification task files and give the product owner a digest route

**Status: Archived, 2026-11-12.** Approved for execution under decision AP1 (autonomous approval of gate `approve-and-execute`). Authored on branch `claude/feat/spec-task-file-digest`, stacked on the unmerged branch `claude/fix/issue-599` (pull request 600), base revision `09cd971e`.
**Development mode:** `test-first` (RED by `test-dev`, GREEN by the implementation specialist, never the same worker).
**Autonomy:** `autonomous` (every open item decided by recommendation; provenance in `## Decisions`).
**Scale:** `extends-component`, components `KyberSquad` (the product-owner and conductor contracts), `KyberArbiter` (the `arbiter plan` command and the task parser) and `CI Pipelines` (the `KW-DOC-TASKS-*` rule reference).
**Delivery:** one pull request on branch `claude/feat/spec-task-file-digest`, targeting `claude/fix/issue-599` until pull request 600 merges.

**Bottom line.** A specification's task file (`<spec-folder>/tasks.json`) is promised an execution digest but nothing checks it and the product owner cannot produce one. This plan makes `docs validate` check it with the same six `KW-DOC-TASKS-*` rules a plan's task file gets, keeps `kyber-weave arbiter plan` as the one digest producer (pointed at the spec's `tasks.md`), and has the conductor hand the digest to the product owner, which runs no shell. It also fixes two spec-grammar parse defects that would otherwise force a valid spec's task file to carry a task that depends on itself.

## Problem and goal

**Problem.**

1. `products/kyber-squad/skills/product-owner/references/tasks-phase.md` says the spec task file carries "the execution digest", but `PlanTaskFileValidator.Validate` walks only `DocType.Plan` documents, so no spec task file is ever validated and none can fail `KW-DOC-TASKS-003`. The conductor's spec path says to "validate it before the first dispatch", which today validates nothing.
2. `product-owner` has no shell on any harness, so it cannot run `kyber-weave arbiter plan`, the only producer of the digest (added by pull request 600). It has no supported way to write a valid digest.
3. The task parser misreads the layout a spec task list actually uses. In `- [ ] 1.1 …` items, a `**Depends on:** none` line followed by `_Requirements: 1.1, 1.2, 1.3_` is read as depending on the requirement ids on that line (1.1 and 1.2 in the installed CLI's output), so task 1.1 depends on itself; and a `**Files:**` bullet list is followed into the `**Acceptance:**` bullet, so backticked symbols such as `ArbiterRule.Shadow` become file scope. Checking a spec task file against that parse would demand the wrong dependencies and files, and a task that depends on itself never dispatches.
4. The spec contracts do not say when the task file is written, what its `plan` field holds, or where a specification says it is Ready.

**Goal.**

1. `docs validate` (and the docs MCP validate tool) checks `<spec-folder>/tasks.json` against `<spec-folder>/tasks.md` with `KW-DOC-TASKS-001` to `-006`, each finding naming the specification's `tasks.md`.
2. `kyber-weave arbiter plan <spec-folder>/tasks.md -f json` is the documented producer of the spec digest, and the `-003` hint names that path.
3. The spec parse of a well-formed spec matches what the author wrote: `Depends on` ends at the next bullet, and a Files bullet list stops at the next bold-labelled bullet.
4. The product-owner and conductor contracts state the finalization order: last `tasks.md` edit, the conductor runs the producer and passes `SPEC_DIGEST`, the product owner writes `tasks.json` in place, validation, then `SPEC_FINALIZED` with `TASK_FILE:`.
